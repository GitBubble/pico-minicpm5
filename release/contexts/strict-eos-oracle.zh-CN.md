# 重新推导严格 EOS 期望

[English](strict-eos-oracle.md)

ctx8192 的记录里长期带着 `eos: FAIL_STRICT_SEQUENCE_MISMATCH`，对照的是这条序列：

```text
[242, 39, 220, 608, 4219, 357, 242, 39, 130073]     " 2\nThe answer is 2"
```

这条序列从未被追溯到参考模型。2026-08-17 用固定 checkpoint
（`openbmb/MiniCPM5-1B`，revision `4e9de7a0778…`）以 float64 贪心解码、遇
`eos_token_id = [1, 130073]` 停止，从板端使用的同一组 prompt id
（`[0] + encode("1+1 equals")`）重新推导，得到：

```text
[242, 39, 220, 608, 4219, 357, 242, 39, 35, 1]      " 2\nThe answer is 2."
```

参考模型写下一个句号然后停止。在分歧的那一步，它以 `0.31` 个 logit 的优势选择
句号——差距明确、且在 float32 与 float64 下给出同一个 token，但并不悬殊：两者
的概率之比是 `1.36:1`。

| token | logit (fp64) | logit (fp32) | 概率 (fp32) |
|---|---:|---:|---:|
| `35` `"."` | 20.183120 | 20.18317 | 39.14% |
| `130073` EOS | 19.877989 | 19.87802 | 28.85% |

所以那条期望是反的。以参考模型为准：

| Profile | 生成序列 | 与参考一致 |
|---|---|---|
| ctx1024 | `[…242, 39, 130073]` | 否——早停一个 token |
| ctx4096 | `[…242, 39, 130073]` | 否——早停一个 token |
| **ctx8192** | `[…242, 39, 35, 1]` | **是，十个 token 全对** |

三次运行共用逐字节相同的 `prefill.om` 与 `head_flat.om`，并在同一个执行器上
进行，因此唯一的自变量是各档自己的 `decode.om`。

## 这件事改变了什么，没改变什么

它把 `eos` 从 ctx8192 的阻塞项里移除：以参考模型而非 ctx1024 的输出为准，
ctx8192 通过，而另外两档带有一个 token 的偏差。

它不代表 ctx8192 已验收。该档的标定仍是 donor 零扩展而非原生，中文 oracle、
内存包络与长 prompt 三项也仍未闭合。它同样不代表 ctx1024 或 ctx4096 有缺陷：
三档的 48 token 三提示词贪心 oracle 全部通过，而此处的偏差只是句末的一个句号，
出现在参考模型本身优势并不悬殊的一步上。

值得留下的教训与出处有关。**一条"期望序列"如果记录自第一个跑出来的工件、而不是
从参考模型推导，它就只会不断确认那个先跑的工件，并把唯一与之不同的那个报成
坏的。**

证据：整合 monorepo 中的
`scripts/pico_aot/minicpm5_strict_eos_oracle_recheck_qualification.json`。
